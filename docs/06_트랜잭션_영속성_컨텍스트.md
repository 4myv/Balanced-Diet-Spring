**트랜잭션이란**
- 여러 DB 작업을 한 묶음으로 만드는 것
- 트랜잭션은 여러 작업을 한 묶음으로 묶어서 작업 중 하나라도 실패하면 되돌리기(롤백)를 하고, 전부 성공하면 확정(커밋)한다
- 묶음 안의 작업은 전부 성공하거나, 하나라도 실패하면 전부 롤백
- 트랜잭션은 기본적으로 언체크 예외가 나면 롤백하고, 체크 예외는 롤백하지 않음
- Balanced-Diet에서는 → "오늘 기록 초기화" 기능
- JpaRepository 기본 메서드는 각자 트랜잭션을 갖고 있음 (`save()`, `findById()` ...)
- 여러 작업을 하나로 묶고 싶은 메서드에 `@Transactional` 어노테이션을 붙임
- `@Transactional(readOnly = true)` → 이 메서드는 읽기만 한다
  - 변경할 때 비교를 위한 처음 모습 기록을 하지 않음
  - 실수로 값을 바꿔도 UPDATE가 나가지 않음 → 이 메서드는 DB를 바꾸지 않는다
- 원칙 : 외부 API를 기다리는 동안 트랜잭션을 열어두지 않는다 
  - `recommendGoal()` 메서드에 트랜잭션을 붙이지 않은 이유
    - Gemini API를 기다리는 메서드이기 때문
    - 메서드 안에서 JpaRepository 기본 메서드를 부르기 때문에 잠시 트랜잭션이 생김
- ```properties
  # 트랜잭션의 시작과 끝에 찍는 로그
  logging.level.org.springframework.orm.jpa.JpaTransactionManager=DEBUG
  ```

**영속성 컨텍스트란**
- JPA가 DB에서 꺼낸 엔티티를 보관해두는 작업 공간 ex) 메모장
  - DB에서 `Profile(id=1)`을 꺼내면 → "1번 Profile은 이 객체"라고 메모장에 적어둠
- 같은 걸 다시 꺼내면 같은 객체를 줌
  - ```java
    Profile a = 꺼내기(id: 1번); 
    Profile b = 꺼내기(id: 1번); 
    a == b      // true - 영속성 컨텍스트에 이미 있으니 같은 객체를 줌
    ```
- 바꾸기만 하면 알아서 저장됨 → `"변경 감지(dirty checking)"`
  - 트랜잭션이 끝날 때, JPA가 원래 모습과 지금을 비교해서 바뀐 게 있으면 UPDATE
  - ```java
    Profile profile = 꺼내기(id: 1번);
    profile.updateGoal(...); // 값을 바꿈
    // save() 메서드를 실행하지 않아도 트랜잭션이 끝날 때 UPDATE 해줌
    ```
- 기본적으로 트랜잭션이 시작하면 영속성 컨텍스트도 시작, 끝나면 같이 버려짐 (OSIV가 켜져 있으면 요청 끝까지 유지)

**개발 중 경험**
- 변수 안에 `find()` 메서드의 반환값을 저장하여 계산하지 않고, 계속 호출하는 코드를 작성함
  - ```java
    find().updateGoal(...);     // 객체를 꺼내서 목표를 업데이트함
    return profileRepository.save(find());  // 다시 꺼내서 저장함
    ```
- `@Transactional`을 붙여 영속성 컨텍스트(메모장)이 하나로 유지되면 두 `find()`는 같은 객체를 꺼내줌
- `@Transactional`이 없으면 메서드를 부를 때마다 영속성 컨텍스트가 따로 생겼다가 버려짐
- 영속성 컨텍스트(메모장)이 매번 새로 만들어진다면 두 객체는 다른 객체이므로 업데이트한 목표가 저장되지 않음
- 위 코드를 작성할 당시에는 `@Transactional`을 붙이지 않았음에도 제대로 작동했음
- 그 이유는 `OSIV(Open Session In View)` 때문

**OSIV**
- 스프링 부트가 기본으로 켜두는 설정
- 켜져 있으면 영속성 컨텍스트가 트랜잭션 동안이 아닌 요청 전체 동안 유지됨
- → `@Transactional`이 없어도 한 요청 안에서는 같은 영속성 컨텍스트를 사용함 
- 그래서 개발 중 `find()`를 여러 번 호출했을 때도 같은 객체가 나왔음
- 켜두면 Controller에서도 DB 데이터를 더 꺼내 쓸 수 있어 편리함
- API 서버에서는 끄는 경우가 많음
  - 왜?
  - 동작이 눈에 보이게 → 트랜잭션을 직접 붙인 곳에서만 영속성 컨텍스트가 유지되니, 개발 중 경험처럼 우연히 동작하는 코드가 사라짐
  - 켜져 있으면 요청이 끝날 때까지 DB 연결을 붙잡고 있을 수 있음 → 이 프로젝트는 Gemini를 최대 30초 기다리는 요청이 있음

**실험 1 - `save()` 빼기**
ProfileService.saveGoal()
<br>
기존
```java
        // 3. 목표 채우기
        profile.updateGoal(...);

        // 4. 저장하고 돌려주기
        return profileRepository.save(profile);
```

변경 후
```java
        // 3. 목표 채우기
        profile.updateGoal(...);

        // 4. 돌려주기 (save 없음 - 트랜잭션이 끝날 때 변경 감지로 UPDATE)
        return profile;
```

메서드 실행 후 콘솔
```
Creating new transaction with name [...ProfileService.saveGoal]
Hibernate: select ... from profile        ← find()로 꺼냄
Initiating transaction commit              ← 메서드가 끝나서 커밋 시작
Hibernate: update profile set ...          ← 커밋하면서 변경 감지 → UPDATE
```
- `save()`를 부르지 않았는데도 `update`가 나감
- 메서드가 끝나고 커밋할 때 JPA가 영속성 컨텍스트의 처음 모습과 현재 모습을 비교해서 변경 감지
  → 바뀐 게 있으니 UPDATE를 보냄

**실험 2 - `@Transactional`도 빼기**
- `save()`가 빠진 상태로`@Transactional`를 빼고 명령어를 보내 목표를 설정한 다음 
  - ```
    curl -X POST http://localhost:9090/api/profile/goal -H "Content-Type: application/json" -d "{\"goalType\":\"bulk\",\"calories\":3000,\"carb\":400,\"protein\":150,\"fat\":90}"
    ```
- 다시 조회해보면
  - ```
    curl http://localhost:9090/api/profile
    ```
  - DB에 반영되지 않고, 콘솔에도 `update`가 안 찍혀 있음
  - 왜 이렇게 되냐면
  - ```
    find()          → 꺼냄 (OSIV 덕분에 메모장에는 계속 남아 있음)
    updateGoal()    → 메모장 속 객체의 값만 바뀜
    return profile  → 바뀐 객체로 응답을 만듦 → 그래서 응답은 3000
    요청 끝         → 메모장 닫힘. 그런데 커밋할 트랜잭션이 없었으니 UPDATE도 없음
    ```
  - 변경 감지는 트랜잭션이 커밋될 때 일어난다. 트랜잭션이 없으면 커밋도 없기 때문에 값을 바꿔도 DB로 가지 않는다.
  <br><br>
- 그래서 `save()`는 빼야 하나?

  |메서드|`save()`|이유|
  |-|-|-|
  |`saveGoal()`|빼도 됨|항상 이미 DB에 있는 Profile을 고치는 거라, 변경 감지로 충분하다|
  |`saveBody()`|남겨야 함|Profile이 없으면 `new Profile()`로 새로 만드는데,<br/>새로 만든 객체는 영속성 컨텍스트에 없기 때문에 변경 감지 대상이 아님. <br/>`save()`로 영속성 컨텍스트에 넣어줘야 INSERT가 나감|
<br>

**"오늘 기록 초기화"를 한 번에 지우는 API**
- 지금은 브라우저가 기록을 하나씩 지워달라고 요청함
- 요청을 따로 처리하는 중에 문제가 발생할 수 있음
- 현재는 요청이 지워야 할 기록 만큼 따로 가니까 하나로 묶을 수 없음 → 그래서 "이 날짜의 기록 전부 삭제"를 요청 하나로 만들고, 트랜잭션으로 묶음
- 실험
  - A - `@Transactional` 없이 만들면? → 에러
    - ```java
      // MealRepository
    
      void deleteByDate(LocalDate date);
      // delete(지워라) By(~로) Date(date 필드) → "date가 같은 행을 전부 지워라"
      ```
      ```java
      // MealService
    
      // 날짜별 전체 삭제 - 당일 기록을 일괄 삭제
      // 일부러 @Transactional 없이
      public void deleteByDate(LocalDate date) {
          mealRepository.deleteByDate(date);
      }
      ```
      ```java
      // MealController
    
      // DELETE /api/meals?date=2026-10-06 - 그 날의 기록 전부 삭제
      @DeleteMapping
      public void deleteByDate(
              @RequestParam @DateTimeFormat(iso = DateTimeFormat.ISO.DATE) LocalDate date) {
          mealService.deleteByDate(date);
      }
      ```
      - 위와 같이 추가하고 작동 모습을 살펴보면
      - (기록 두 개를 추가하고 아래 명령어로 해당 날짜 기록을 삭제해본다) 
      - `curl -i -X DELETE "http://localhost:9090/api/meals?date=2026-10-06"`
      - status: 500
      - Caused by: No EntityManager with actual transaction available for current thread - cannot reliably process 'remove' call
      - 진행 중인 트랜잭션이 없어서 삭제를 처리할 수 없다는 뜻
      - `JpaRepository`를 상속받은 `repository` 안의 메서드이더라도, 직접 이름으로 만든 메서드(findByDate, `deleteByDate`)는 기본 메서드와 달리 트랜잭션이 자동으로 붙지 않는다 <br>
        → 그래서 바깥에서 `@Transactional`을 붙여 트랜잭션을 열어줘야 함
      <br><br>
  - B - `@Transactional` 붙이기
    - 위와 같은 테스트를 다시 해보면
    - status: 200
    - console: 
      ```
      Creating new transaction with name [...MealService.deleteByDate]
      Hibernate: select ... from meal where date=?     ← 그 날짜 기록을 먼저 찾고
      Initiating transaction commit
      Hibernate: delete from meal where id=?            ← 하나씩 지우는데
      Hibernate: delete from meal where id=?            ← 전부 같은 트랜잭션 안
      ```
    - 삭제 두 번이 트랜잭션 하나 안에서 일어남
    - `deleteByDate`는 찾아서 하나씩 지우는 방식이라 기록의 수만큼 `delete`가 사용됨
    <br><br>
  - C - 도중에 에러가 발생하면?
    - 트랜잭션의 핵심! 전부 아니면 전무 → 전부 커밋 또는 전부 롤백
    - 실험용 코드 추가
      - ```java
        // 날짜별 전체 삭제 - 당일 기록을 일괄 삭제
        @Transactional 
        public void deleteByDate(LocalDate date) { 
        mealRepository.deleteByDate(date); 
        throw new IllegalStateException("롤백 실험");   // 실험용 추가, 일부러 에러를 던짐 
        // IllegalStateException은 RuntimeException의 자식, 언체크 예외
        }
        ```
    - 이후 위 두 테스트와 같은 방식으로 메서드를 실행해보면
    - status: 500
    - console:
      ```
      Creating new transaction with name [...MealService.deleteByDate]
      Hibernate: select ... from meal where date=?
      Initiating transaction rollback               ← 커밋이 아니라 롤백
      ```
    - 메서드 실행이 끝나고 조회해보면
    - `curl "http://localhost:9090/api/meals?date=2026-10-06"`
    - 앞서 저장한 두 기록이 그대로 있음 <br> 
    → 트랜잭션 안에서 언체크 예외가 발생했기 때문에 전부 롤백됨
    <br><br>
- script.js의 "오늘 기록 초기화" 부분
- ```javascript
      try {
        for (const meal of state.meals) {
            await callApi("DELETE", "/api/meals/" + meal.id);
        }
  ```
  ↓
- ```javascript
      try {
        await callApi("DELETE", "/api/meals?date=" + getTodayString());
        }
  ```
  - for문이 사라지고 요청 한 번이 됨
  <br><br>
  
**OSIV 끄기**
- `application.properties`에 추가
  - ```properties
    # OSIV 끄기 - 영속성 컨텍스트를 요청 전체가 아니라 트랜잭션 동안만 유지
    spring.jpa.open-in-view=false
    ```
- 확인
  - 트랜잭션 로그가 바뀜
   
  ||OSIV 켜짐|OSIV 꺼짐|
  |-|-|-|
  |시작|`Found thread-bound EntityManager`|`Opened new EntityManager`|
  |끝|`Not closing pre-bound JPA EntityManager`|`Closing JPA EntityManager`|
  - OSIV가 켜져 있었을 때는 "이미 묶여 있던 영속성 컨텍스트를 찾았다"/"안 닫는다"였는데,
  - OSIV를 끄고 난 뒤 로그는 "영속성 컨텍스트를 새로 열고"/"닫는다"로 바뀌었음
<br> → 영속성 컨텍스트의 수명이 트랜잭션과 같아짐 
  ```
  OSIV 켜짐:  요청 시작 ─────── 메모장 하나 ─────── 요청 끝
  OSIV 꺼짐:  요청 시작 ─ [트랜잭션: 메모장] ─ 요청 끝   ← 지금
  ```
- 기능은 그대로
  - 저장이 필요한 메서드엔 `@Transactional`을 붙여서, 트랜잭션이 끝날 때 커밋되어 영속성 컨텍스트의 변경 내용이 DB에 반영되기 때문
  - Controller는 트랜잭션이 끝난 뒤에 엔티티에서 값을 꺼내 DTO로 만듦 (이때 영속성 컨텍스트는 이미 닫혀 있음)
  - 그래도 되는 이유: 엔티티의 필드가 키, 이름, 칼로리 같은 단순한 값이라 DB에서 꺼낼 때 이미 객체에 다 들어와 있음
  
- OSIV를 끄면 생길 수 있는 문제 (아직 프로젝트에선 해당 없음)
  - 엔티티끼리 연결되면(연관관계), 연결된 쪽을 필요할 때 꺼내는 "지연 로딩"을 씀
  - 트랜잭션이 끝난 뒤 Controller에서 그걸 꺼내려 하면 영속성 컨텍스트가 닫혀 있어서 `LazyInitializationException`
  - 해결: Service의 트랜잭션 안에서 미리 꺼내 DTO로 만들어 돌려주기
  - 사용자가 여러 명이 되면(로그인 기능) 다시 다룰 것
